# Kotlin Compiler Internals Reference

Read this file for compiler implementation, K1/K2 migration, FIR, resolution, diagnostics, IR, lowerings, JVM/JS/Wasm/Native backends, code generation, and compiler test-data work.

## Localize the phase

Use the pipeline below to decide where evidence belongs:

```text
text -> lexer/parser/PSI -> frontend resolution and typing -> diagnostics -> FIR/IR -> lowerings -> backend codegen -> artifact -> runtime
```

A parser issue needs test data and PSI/parser evidence. A type or diagnostic issue needs frontend symbols, scopes, resolution, and diagnostic rendering. A generated-code issue needs FIR/IR dumps, lowering order, backend code generation, and artifact inspection. A runtime issue needs a minimal generated artifact and target runtime reproducer.

## K1 and K2/FIR

Determine whether the issue is expected to affect the legacy frontend, K2/FIR, or both. Keep fixes in the frontend that owns the behavior. Compare diagnostics, smart casts, overload resolution, type inference, contracts, and error recovery across frontend modes when the repository supports both. Do not port a K1 workaround into FIR without understanding the semantic contract.

## FIR and Analysis API

FIR represents frontend information and resolution state. Follow the local symbol, session, scope, checker, and diagnostic conventions. Analysis API clients must respect session lifetime, invalidation, symbol ownership, and threading. Do not retain PSI, symbols, types, or sessions beyond their documented lifetime.

## IR and lowerings

When changing IR, inspect the IR element contract, symbol ownership, parent relationships, origin, type substitution, annotations, and lowering order. Keep transformations deterministic. Check whether the change affects all backends or only JVM, JS, Wasm, or Native. Add an IR or backend test that demonstrates the semantic behavior rather than relying only on a textual dump.

## Diagnostics

Treat diagnostic factories, severity, source ranges, messages, suppression, rendering, and IDE consumers as a coordinated API. Keep diagnostic tests small and use repository directives for frontend, backend, language version, and target. If a diagnostic is changed intentionally, update all expected outputs through the project’s prescribed process.

## Backend and artifact inspection

| Backend | Inspect |
| --- | --- |
| JVM | Generated bytecode, signatures, annotations, invokedynamic, metadata, and Java runtime behavior |
| JS | JS IR, generated modules, names, source maps, npm interop, and browser/Node runtime |
| Wasm | Wasm artifact, JS/WASI glue, exports, memory/runtime features, and browser/WASI behavior |
| Native | LLVM/linker output, framework headers, symbols, architecture, SDK, and final consumer |

## Compiler test-data workflow

Find a neighboring test with the same feature and backend. Add the smallest source file and expected output. Preserve directives and generated-runner conventions. Run the focused test task, regenerate test runners only when required, inspect the diff, and then run the broader suite justified by the change. Never edit generated test runners directly.

## Debugging checklist

Capture source, compiler version, language/API version, frontend mode, backend, flags, target, dependencies, expected result, actual diagnostic or artifact, and execution environment. Reproduce with the command-line or repository test harness before altering several phases. Use dumps or instrumentation only at the narrowest phase needed.
