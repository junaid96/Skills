# Kotlin Compiler Internals Reference

Read this file after `compiler-and-analysis.md` has localized a compiler problem and the task requires contributor-level implementation detail. This reference owns deep compiler phases, FIR internals, IR transformations, backend implementation, internal debugging, and compiler-development workflows. It intentionally does not repeat the high-level pipeline, repository area map, or user-facing diagnostic orientation.

## Ownership boundary

`compiler-and-analysis.md` owns compiler architecture orientation, FIR/K2 concepts, IR overview, frontend/backend relationships, Analysis API, PSI, IDE/JPS relationships, practical routing, minimal user-facing diagnosis, and ordinary troubleshooting. This file owns the deeper implementation mechanics below. Load only this file when the phase is already known and the task requires internals.

## FIR internals

When working in FIR, identify the relevant declaration, symbol, session, scope, checker, resolve phase, tower-resolution behavior, lazy body, diagnostic factory, or generated declaration. Preserve symbol ownership and session lifetime rules. Determine whether the change affects resolution, type inference, contracts, smart casts, overload resolution, diagnostics, expect/actual matching, or conversion into IR. Compare K1 and K2 only when the repository still supports both behaviors for the affected test.

Do not port a K1 workaround into FIR without understanding the semantic contract. Prefer a focused FIR test or existing checker/resolution fixture and follow local phase and diagnostic conventions.

## IR lowering and transformations

When changing IR, inspect element contracts, symbol ownership, parent relationships, origins, type substitution, annotations, default arguments, value-class behavior, inline functions, suspend lowering, and lowering order. Determine whether a transformation is common or backend-specific. Keep transformations deterministic and preserve metadata and source information required by downstream consumers.

Add an IR or backend test that demonstrates semantic behavior rather than relying only on a textual dump. Inspect generated bytecode, JavaScript, Wasm, Native, or other artifacts when the change can affect consumers or runtime behavior.

## Backend implementation

| Backend | Deep implementation concerns |
| --- | --- |
| JVM | IR-to-bytecode lowering, signatures, annotations, invokedynamic, metadata, JVM version, and runtime linkage |
| JS | JS IR, klibs, module/name generation, source maps, npm interop, bundling, and browser/Node runtime |
| Wasm | Wasm lowering, exports, JS/WASI glue, memory/runtime features, binary layout, and browser/WASI behavior |
| Native | LLVM lowering, linker inputs, target architecture, framework headers, symbols, ABI, memory/runtime behavior, and final consumer |

Check all affected backends or document why a phase is target-specific. Do not assume a common IR change has identical runtime behavior on every backend.

## Compiler phases and instrumentation

Localize the smallest phase that can explain the behavior: parsing, frontend resolution, diagnostics, FIR-to-IR conversion, lowering, backend code generation, artifact packaging, or runtime linkage. Use repository-supported dumps, phase tracing, instrumentation, or debug flags only at that boundary. Keep instrumentation temporary unless it is itself an intentional diagnostic feature.

Avoid changing multiple phases at once. Preserve phase ordering and invariants. When a crash or incorrect artifact appears late, inspect the earliest invalid invariant rather than patching only the final symptom.

## Internal debugging workflow

1. Record compiler revision, language/API version, frontend mode, backend, target, flags, host, dependencies, and expected behavior.
2. Reduce the source to the smallest reproducer that preserves the failing phase.
3. Locate the responsible phase, symbol/IR invariant, lowering, backend, or artifact boundary.
4. Find neighboring implementation and test patterns in the same subsystem.
5. Add the smallest regression test using the repository’s directives and harness.
6. Instrument or dump only the relevant phase and compare expected semantic output.
7. Run the focused compiler/backend test, inspect generated artifacts, and run broader tests justified by the change.
8. Review diagnostics, generated files, test runners, and cross-backend effects before proposing the patch.

## Contributor-level test mechanics

Preserve test-data conventions, directives, expected diagnostics, golden outputs, backend markers, and generated-runner policy. Never hand-edit generated test runners. Regenerate them only through the documented task and review unrelated changes. For compiler-plugin or backend changes, test the consumer path users actually invoke, not only an internal unit.
