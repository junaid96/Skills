# Kotlin/JVM and Android Reference

Read this file for JVM applications and libraries, Android applications and libraries, Java interop, JVM bytecode, Android Gradle Plugin integration, and platform-specific tests.

## Project triage

Inspect the Gradle wrapper, Kotlin and Android Gradle Plugin versions, Java toolchain, compile SDK/min SDK, module type, source sets, build variants, and whether the module is an application, JVM library, Android library, or KMP module. Preserve the existing version matrix unless the request is explicitly a migration.

| Project | Primary plugins and files | Main risks |
| --- | --- | --- |
| JVM application | `kotlin("jvm")`, `application`, `build.gradle.kts` | JDK/runtime, entry point, packaging, Java interop |
| JVM library | `kotlin("jvm")`, `java-library`, `maven-publish` | API/ABI, toolchain, metadata, variant publication |
| Android application | Android application plugin, `src/main`, manifests/resources | SDK levels, variants, shrinking, lifecycle, permissions |
| Android library | Android library plugin, consumer rules, resources | ABI, resource names, manifest merging, publishing |
| KMP Android target | KMP plus the current Android KMP library plugin when applicable | Target DSL migration, source-set graph, test configuration |

## JVM toolchain and target alignment

Use a Gradle Java toolchain and align Kotlin `jvmTarget` with Java `targetCompatibility`. If compilation fails with a JVM-target validation error, inspect both Kotlin and Java compile tasks and the effective toolchain rather than suppressing validation. Check the `.kotlin` project data directory and ensure it is ignored by version control.

A minimal JVM library configuration is conceptually:

```kotlin
plugins {
    kotlin("jvm")
    `java-library`
}

group = "com.example"
version = "0.1.0"

kotlin {
    jvmToolchain(17)
}
```

Use the project’s actual Kotlin version and required JDK; the version above is illustrative only.

## Java interoperability

At a Java boundary, review platform types, nullability annotations, checked exceptions, SAM conversion, default arguments, overloads, `@JvmName`, `@JvmOverloads`, `@JvmStatic`, `@JvmField`, value classes, sealed hierarchies, generic variance, and generated method names. Add a Java consumer test when the public API is intended for Java callers. Do not expose Kotlin-only implementation details accidentally through a published Java-facing API.

When Java calls Kotlin, inspect decompiled signatures or generated bytecode if a name, overload, generic, annotation, or nullability issue is suspected. When Kotlin calls Java, treat unannotated types as uncertain and validate null behavior at the boundary.

## Android architecture and build boundaries

Keep Android lifecycle, UI, permissions, resources, services, and platform storage in Android-specific modules or source sets. Keep domain logic and deterministic transformations in ordinary Kotlin or `commonMain` when appropriate. For Compose UI, distinguish Compose runtime/state concerns from Android windowing, navigation, lifecycle, and accessibility integration.

For variant failures, compare the requested variant, flavor dimensions, build type, manifest merging, generated sources, resource overlays, and consumer ProGuard/R8 rules. For release-only failures, inspect shrinking, reflection, serialization, resource packaging, and signing before changing business logic.

## Android tests

Use local JVM tests for deterministic logic, instrumented/device tests for Android framework behavior, and a KMP Android host/device test configuration when the project uses the current KMP Android library plugin. Test permissions, configuration changes, process recreation, serialization, lifecycle cancellation, and resource qualifiers when those are part of the behavior.

## Publishing and compatibility

For JVM libraries, configure `maven-publish`, sources and documentation artifacts when required, API/binary compatibility checks, POM metadata, and a representative downstream consumer. For Android libraries, verify AAR contents, manifest/resource behavior, consumer rules, variant publication, and minimum SDK. Never infer published compatibility only from a successful local compile.

## Diagnostic sequence

1. Record Kotlin, KGP, Gradle, JDK, AGP, SDK, and device/emulator versions.
2. Reproduce with the narrowest task and variant.
3. Run `./gradlew dependencies` or the appropriate dependency report when resolution is involved.
4. Inspect compiler task options, generated sources, merged manifests/resources, and packaged artifacts.
5. Compare debug and release behavior when shrinking or packaging is suspected.
6. Add a focused JVM, Android, or downstream-consumer test before applying a broad configuration change.
